# Big Balls Sports Data: NBA provider spike

**Research date:** 2026-11-17 · **Branch base:** `origin/main` at `229c994`

**Scope:** provider discovery and smoke tests only. No backend, frontend, D1 rows, or existing provider configuration were changed. No DunkAPI requests were made. No subscription or GitHub OAuth was purchased or enabled.

## Decision

**Conditional GO for a cached BuzzerBoard data-layer prototype; NO-GO for switching the public production product today.** The free key returned current 2026-27 schedules, scores, period lines, team and player box scores, current-season player averages, and player profiles in the tested samples. For the existing product surfaces, a server-side refresh appears to need tens of requests per day, not a tight credit budget. The documented Free ceiling is 1,000 requests/day and 100/minute; this key reported a 2,000/day limit and 100/minute. Neither figure is an unlimited or guaranteed production allowance. [Pricing](https://bigballsdata.com/pricing), [rate limits](https://bigballsdata.com/docs/rate-limits)

The research found material gaps before BBS can replace the current provider end to end:

1. The 2026-27 standings endpoint returns 30 teams, but all 30 have a null conference and it omits `games_back`, home/away records, and last-10 fields. Those columns cannot be rendered from that response. The per-team season endpoint contains more of them, but only two team samples were checked; a full standings build may require one request per team and a separately synchronized join.
2. The documented NBA team filter returned 84 rows, only 30 of which joined to the current 30 standings teams. The extra rows included non-current/historical entities. Use standings IDs as the current-season identity list until the directory filter and intended archive semantics are clarified.
3. `GET /v1/players/{id}` returned HTTP 400 for a UUID just returned by player search. The documented `/profile` route worked for all three samples. Player logs returned useful current-season rows, but do not include every field in the per-game box score.
4. Published NBA/player-stats pages still describe 2025-26 or September ingestion, while the live coverage catalogue and authenticated requests show 2026-27 data. The live samples were fresh, but this documentation drift needs an operational freshness commitment.
5. BBS Terms allow displaying data to a product’s own readers and prohibit raw-feed redistribution, but the materials reviewed do not establish BBS’s right to sublicense NBA statistics, team marks, or logos for this use. NBA.com’s terms place restrictions on displaying comprehensive, regularly updated NBA-statistics databases absent express consent. This is a launch blocker until the rights chain is confirmed in writing. This is a product-risk finding, not legal advice. [BBS Terms](https://bigballsdata.com/legal/terms), [NBA Terms](https://www.nba.com/termsofuse)

## Current-cache comparison

The local D1 `dunkapi:nba:games:date=2026-11-15` record contains 9 final games. BBS returned 9 finished rows for that same NBA date. The multiset of the 9 home/away score pairs matched the D1 values; a full team-ID crosswalk was not established because BBS IDs are provider-scoped UUIDs and the D1 cache has DunkAPI-scoped IDs. Do not join on those IDs or combine source snapshots.

Three BBS game boxes were sampled (two on Nov 15 and one on Nov 16). The returned player counts were 26, 19 and 25; all three had four periods, zero unassigned player rows, and point totals that reconciled to the team boxes. The selected games returned player rows only; availability/lineup data is a separate endpoint.

## Request-budget model

The request budget belongs to the server-side provider refresh, not each page view. D1 caching and deduplication are still required.

| Workload                                   | Approximate provider requests/day | Basis                                                                                                                                       |
| ------------------------------------------ | --------------------------------: | ------------------------------------------------------------------------------------------------------------------------------------------- |
| Game Center dates: today + next 7 dates    |                                 8 | `/v1/matches` accepts one `date` per request; each tested page held the whole date                                                          |
| Standings refresh                          |                                 1 | One current-season `/v1/standings` response                                                                                                 |
| Completed-game player boxes                |               7 typical / 15 busy | One box endpoint per final game; the tested endpoint returned both teams together                                                           |
| **Core busy-day total**                    |                            **24** | 8 + 1 + 15, before occasional reference refreshes                                                                                           |
| All-player season averages refreshed daily |        roughly 450–850 additional | One request per player if no bulk route can be confirmed; coverage reports 857 player-season rows, not a verified unique-player denominator |
| All-player game logs refreshed daily too   |           roughly another 450–850 | One request per player; this is unnecessary if logs are populated from cached game boxes                                                    |

At the core workload, Free has ample headroom and does not require constant request rationing. Refresh player averages on a longer TTL and load player profiles/logs on demand; game boxes already carry the current per-game lines. Refreshing averages and logs for every player every day could exceed the 1,000/day base tier; even the observed 2,000/day key should retain a safety margin for retries, corrections, growth, and unrelated key usage. Use response `X-RateLimit-*` headers, keep below 100/min, stop on 4xx, and honor `Retry-After`. The documented daily bucket resets at UTC midnight. [Rate-limit guidance](https://bigballsdata.com/docs/rate-limits)

## Terms and rights

BBS Terms effective 2026-08-10 allow storing responses, internal models and displaying statistics to readers of an app/dashboard; they prohibit selling/republishing raw fields as an API, feed, file or bulk export. BBS also states the service is “as is” and does not warrant accuracy/completeness/availability. Its public licence-notices page reviewed here lists other datasets but no NBA data attribution or NBA/club-mark grant. [BBS Terms](https://bigballsdata.com/legal/terms), [licence notices](https://bigballsdata.com/attribution)

NBA.com Terms require prominent attribution and limit NBA statistics to specified purposes; they restrict comprehensive regularly updated statistical databases without express consent. Therefore BBS’s own permission to display its API response is not evidence that all upstream NBA data rights have been sublicensed. Confirm the provenance and written rights for statistics, current/derived data, team logos and player images with BBS and the NBA rights holder before a public launch. Track the broader marks/data review in [PRO-181](https://linear.app/generation17/issue/PRO-181/bb-proverit-prava-dunkapi-upstream-i-nba-brendinga-pered-publichnym). [NBA Terms](https://www.nba.com/termsofuse)

## Recommendation and migration gate

1. Keep the present DunkAPI/Worker/D1/Vue behavior unchanged. Do not change provider defaults based on this spike.
2. Ask BBS to confirm in writing: NBA data-source/licensing chain for public display; team logo and player-image rights; whether `teamId` intentionally includes former team memberships; why the team list includes 84 rows for the documented NBA filter; the supported player profile route; and which freshness/uptime guarantees apply to Free.
3. If the rights review clears, build a separate BBS adapter in a follow-up issue. Keep provider-scoped UUIDs and numeric archive IDs distinct, establish an explicit verified crosswalk, normalize numeric strings/nulls, and never merge BBS/DunkAPI game or box-score snapshots. Store a source namespace in cache keys, validate game/team/date/score identities, and measure real cache freshness.
4. Pilot only the verified current-season capabilities behind a per-capability provider flag. Start with schedules/results and standings basics; fill standings splits through `team-season` only after testing all 30 teams and snapshot consistency. Add player/profile and box-score routes only after regression fixtures cover corrections, DNP, lineup status, nullable fields, score totals and 429 behavior.
5. Use one refresh per date/team/player TTL, lazy player logs, per-game box scores, and the live quota headers. Never connect GitHub OAuth or change plans automatically.

**Final gate:** free BBS appears sufficient for the core current-season Game Center and sampled match details at expected request volume. It is not yet a complete, legally cleared replacement for all BuzzerBoard standings and team/player surfaces. Revisit after written rights confirmation and a fixture-backed adapter PoC.

## Reproduction

`node scripts/bbs-smoke.mjs` prints the no-network request plan. Authenticated requests require explicit `--execute`; the script reads `BBS_API_KEY` from the environment or ignored `.dev.vars`, hard-caps one run at 60 GETs, preserves at least 25 requests of quota when headers are available, stops on the first error, and never logs or saves response bodies. CI should not execute network requests.

No real response payloads or screenshots are committed. Synthetic fixtures remain the right material for CI.
